| | 내용 평가 | 발표 스타일 | 총점 |

### 성격이 반대인 것을 나란히 두지 않는다

> **워크시트는 내는 것이 아니라 듣는 것입니다** — 설명에 한 줄을 박았다.

웹판 **맨 아래에 저장 · PDF 칸을 하나 더** 뒀다. 다 채운 자리에서 위로 되돌아가지 않아도 된다.

## 7. PBL — **방금 본 것에 이름을 붙였다**

사용자가 아홉 기업 카드를 통째로 붙여 놓고 물었다 — **「이런 게 문제별 접근이라는 점을 알려주려면 PBL 어떻게 말하면 좋을까?」**

답은 이미 페이지에 있었다. 아홉 카드가 전부 **문제 두 줄 → 해결 두 줄**이고,
맺음말에 「**"무슨 기술을 쓸까"가 아니라 "누가 어떤 순간에 곤란한가"를 먼저 적는다**」가 적혀 있었다.
**그게 곧 PBL 의 정의**여서, 용어를 새로 가르치는 대신 **이름만 얹기로** 했다.

### 초록 상자 하나 — 일곱 칸

```
1) 다섯 분야는 한 공간의 층   오기 전(주차) · 움직일 때(지도) · 쓸 때(결제) …
2) 순서가 거꾸로다            새 기술을 발명한 곳은 하나도 없다
3) 답이 교과서에 없다          찾아봐야 알고, 정답이 하나도 아니다
4) 막힌 것이 자료다            줌 15 경고 · 안 나오는 자원 → 신청서 [3][6] 칸
5) 기술이 없어도 시작된다      「개발을 못 해서요」는 쓸 수 없는 말
6) 세 과제가 한 줄이다         도시 카드 → 안동 실습 → 응모신청서
7) 과제에 쓰는 법              문제 두 줄, 해결 두 줄이면 충분
```

**힘이 실린 곳은 4번이다.** 학생이 안동 실습에서 막히는 순간을 **실패가 아니라 성과**로 뒤집고,
그것이 응모신청서 어느 칸에 들어가는지까지 이어 붙였다.

### 처음엔 따로 세웠다가 합쳤다

상자를 만들고 보니 **바로 앞 문단과 같은 말을 두 번** 하고 있었다.

| 겹친 말 | 어디에 |
|---|---|
| 「새 기술을 발명하지 않았다」 | 앞 문단 + 상자 2번 칸 |
| 「문제 두 줄, 해결 두 줄」 | 앞 문단 + 상자 맺음말 |

사용자가 **「하나의 초록색 그리드 안에 넣어라」**고 해서 앞 문단을 상자 안으로 들였고,
합치면서 겹친 곳이 사라졌다.

> **교훈 — 새 상자를 세울 때는 옆 문단이 같은 말을 하고 있지 않은지 먼저 본다.**
> 요약을 덧붙이면 원래 있던 요약과 부딪친다.

「한 가지 주의」(다비오 · 딥파인 중복)는 **배우는 방식이 아니라 자료를 세는 법**이라
일곱 칸에 섞지 않고 맨 아래 별도 줄로 뒀다.

## 9. 상자 밖으로 삐져나간 칸 — **`min-width`** (겹침의 원인은 아니었다 → 11절)

사용자가 **「점과 글자가 겹쳐 있어」**라 했다. 용인 상자의 세 갈래 줄이다.

원인은 **내가 두 시간 전에 만든 것**이었다. 왼쪽 정렬로 바꾸면서
`flex: 1 1 0`(반반 나눔) → `flex: 0 1 auto`(글 길이만큼)로 고쳤는데,
`flex-basis: auto` 가 되자 **`min-width: auto` 가 살아나 칸이 제 글 길이 아래로 줄지 못했다.**
두 칸이 상자 폭을 넘어 **밖으로 삐져나갔고**, 그 자리에서 가운뎃점이 옆 글자와 겹쳐 보였다.

```css
min-width: 0;              /* 줄어들 수 있게 — 핵심 */
flex-wrap: wrap;           /* 넘치면 줄을 바꾼다 */
overflow-wrap: anywhere;   /* PLATFORM+RESEARCH 가 통째로 밀지 않게 */
```

> **교훈 — `flex-basis` 를 `0` 에서 `auto` 로 바꾸면 `min-width: 0` 을 같이 넣는다.**
> 플렉스·그리드 칸은 기본값이 `min-width: auto` 라, 줄지 못하고 밖으로 나간다.

**다만 이것은 겹침의 원인이 아니었다.** 고칠 값어치는 있었으나 신고받은 증상은 그대로였고,
진짜 범인은 **글머리 점**이었다 — 11절.

## 10. 척도개발 여덟 장 — **글을 넘기는 캐러셀** (뒤에 걷어냄 → 13절)

사용자가 기존 여덟 장 만화 캐러셀을 가리키며 물었다 —
**「여기처럼 좌우로 움직이는 PPT 슬라이드 형식으로 웹에 제시한다면?」**

둘은 만드는 법이 다르다.

| | 기존 여덟 장 | 척도개발 여덟 장 |
|---|---|---|
| 내용물 | 완성된 **그림**(webp) | **표 10개 + 글** |
| 슬라이드로 | 이미 있음 | **HTML 로 새로 짬** |

**HTML 쪽이 오히려 낫다** — 글자가 선택·복사되고, 좁은 화면에서 안 뭉개지고,
내용을 고칠 때 이미지를 다시 만들 필요가 없다.

```
1 이 노트로 무엇을 얻나      5 요인 패턴 한눈에
2 척도는 어떻게 만들어지나    6 공통과 차이 네 덩어리
3 핵심 요인 여덟 용어        7 기억할 셋과 30초 셀프체크
4 5개 산업 비교             8 부록 장면 그림
```

**움직임은 한 줄도 새로 짜지 않았다.** 기존 스크립트가 `document.querySelectorAll('.stcomic')`
으로 **모든 캐러셀을 순회**하게 돼 있어, 같은 클래스만 붙이니 버튼 · 점 · 키보드 · 스와이프가 그대로 붙었다.

> **교훈 — 스크립트를 id 가 아니라 클래스 순회로 짜 두면 둘째가 공짜로 붙는다.**
> 이 구조는 이전에 누군가 「id 대신 .stcomic 을 돌며 각자 안에서만 찾는다」고 주석까지 달아 뒀다.

**5장이 잘 나왔다.** 편의성과 스마트인프라 두 줄만 바탕을 칠해서,
**다섯 산업 모두에 든 둘**이 8×5 격자에서 바로 보인다.

부록 그림은 워드 안의 PNG 를 꺼내 webp 로 바꿨다 — **1,926KB → 264KB, 86% 감소.**

## 11. 글머리 점 하나가 **세 곳에서 글자를 덮고 있었다**

오늘 가장 오래 끈 버그다. 사용자가 세 번에 걸쳐 말했다 —
**「점과 글자가 겹쳐 있어」** → **「도시를 앞에 중간 점이 있어」** → **「중간 점 없애고 넘버링 해줘」**.

### 처음엔 엉뚱한 것을 고쳤다

첫 신고에 `min-width` 를 의심했다. 실제로 그것도 문제였고(칸이 상자 밖으로 삐져나갔다)
고친 것은 맞지만, **겹침의 원인은 아니었다.**

### 진짜 범인

`learn.css:704`

```css
.learn-article .case-box li::before {
  content: ""; position: absolute; left: 0; top: 8px;
  width: 5px; height: 5px; border-radius: 50%; background: #9fc0e2;
}
```

`.case-box` 안의 **모든 `<li>`** 에 파란 점을 찍는다. 같은 규칙의 `padding-left: 13px` 가
그 점 자리를 비워 두는데, **내가 만든 세 목록은 모두 `padding` 을 0 으로 덮어썼다.**
그래서 점이 `left: 0` 에 그대로 찍혀 **첫 글자 위에 얹혔다.**

| 어디 | 덮인 글자 |
|---|---|
| 용인 상자 세 갈래 줄 | 「**도**시를 가른…」 |
| PBL 상자 일곱 칸 | 「**다**섯 분야는…」 등 |
| 척도개발 상자 네 칸 | 「**다**섯 산업의 공통」 등 |

`content: none` 세 줄로 끝났다.

### 그 사이 번호를 뺐다가 되살렸다

아침에 **「점 없애줘」**를 **번호(`1)` `2)`)를 빼라**는 뜻으로 읽고 척도개발 상자의 번호를 뺐다.
**오진이었다.** 눈에 걸리던 점은 번호가 아니라 글머리 점이었다.
점을 없앤 뒤 사용자가 **「넘버링 넣어줘」**라 해서 되살렸다 — PBL 도 같은 길을 갔다.

> **교훈 — 「점이 보인다」는 말에는 점이 여럿 있다.**
> 글머리 점 · 번호 뒤 괄호 · 가운뎃점 셋 중 무엇인지 먼저 물었어야 했다.
> 물었을 때(AskUserQuestion) 사용자는 「번호」를 골랐지만, 실제로 보고 있던 것은 글머리 점이었다 —
> **선택지에 그 항목이 없었다.** 화면 문제는 선택지를 내 추측으로 좁히면 안 된다.

## 12. 줄글을 다섯 군데 더 끊었다

3절에서 셋을 끊었고, 오후에 **다섯**을 더 끊었다. 이제 이 페이지의 긴 설명은
거의 다 「**번호) 키워드 : 요약**」이다.

| 어디 | 칸 |
|---|---|
| 과제 1 알약 줄 설명 | 다섯 — 양식 둘 중 하나만 / 예시는 견본 / 워크시트는 듣는 것 / 평가는 40점 / 낼 것은 PDF |
| 관광AI 문제해결 공모 | 여섯 — 누가 / 융합 팀에 가점 / 분야 둘 / 떨어져도 남는 것 / 배점 / 그래서 무엇을 쓰나 |
| 데이터랩 활용 경진대회 | 넷 — 무엇을 내나 / 시상 / 이 수업과 맞는 곳 / 주의 |
| 지역관광 문제해결 해커톤 | 여섯 — 구조가 둘 / Section 1 / 아이디어만 / 상금 / 왜 낯익은가 / 다음 회차 |
| AX 공모(8절) | 일곱 |

**공모 카드 넷이 같은 모양(`ax-kw`)으로 읽힌다.** 마감 · 자격 · 제출물이 늘 같은 자리에 온다.

각 카드에서 **맨 앞 칸을 무엇으로 둘지**가 판단이었다 —
데이터랩은 「**개발 실력을 겨루는 대회가 아니다**」, 해커톤은 「**학생이 볼 곳은 Section 1**」.
학생이 첫 줄에서 자기와 상관있는지 가려낼 수 있어야 한다.

## 13. 척도개발 복습 — **네 번 갈아엎었다**

오늘 가장 많이 손댄 자리다. **캐러셀 → 걷어냄 → 슬라이드 → 덱**.

| 시도 | 무엇 | 왜 물렀나 |
|---|---|---|
| ① 여덟 장 캐러셀 | 글·표를 `.stcomic` 으로 | 사용자: **「캐러셀 없애줘」** |
| ② 걷어냄 | 상자를 원래대로 | |
| ③ 슬라이드 둘 | 그림 11장 HTML + PPTX | 그대로 둠 — 강의실에서 띄우는 판 |
| ④ **덱 11장** | 파트 05 와 같은 부품 | **최종** |

### 스크립트를 고쳐야 했다

캐러셀은 클래스를 순회(`.stcomic`)해서 둘째가 공짜로 붙었는데, **덱은 아니었다.**

```js
전  var deck = document.getElementById('deck');      // 하나만
후  document.querySelectorAll('.deck').forEach(…)    // 전부
```

11절에 적은 교훈이 **바로 다음 절에서 값을 치렀다** — 캐러셀은 이미 클래스 순회였고,
덱은 아니어서 여섯 줄을 고쳐야 했다. 파트 05 덱은 그대로 돌고, 앞으로 덱을 더 세워도 따라붙는다.

### 기존 부품을 거의 그대로 썼다

`logic` · `neg` · `pos` · `chain` · `formula` · `aim` · `tbl-wrap` · `ref` 표 · `f3-why`.
**새로 만든 것은 덱 안 키워드 목록(`sc-dk`)과 표 변형(`sc-tb`) 둘뿐**이고,
`sc-dk` 에는 **글머리 점 막는 줄을 미리 넣었다**(11절에서 세 번 당한 뒤라).

**02장에 `neg`/`pos` 대비를 넣었다** — 파트 05 가 「앱 제공 ✕ / 도시 관리 ○」로 쓰는 형식을
「첨단기술 보유 ✕ / 경험되는 스마트함 측정 ○」으로 옮겼다. 같은 페이지의 같은 문법이다.

### 내용은 PPTX 에서 뽑았다

그림 11장짜리 HTML 에는 글이 없어 쓸 수 없었고, **PPTX 슬라이드 XML 의 `<a:t>` 를 긁어**
열한 장의 글을 모두 확보했다. 9장 그림은 아까 워드에서 꺼내 두었던 **webp(264KB)** 가 쓰였다 —
캐러셀을 걷으며 버릴까 했던 것이 여기서 제자리를 찾았다.

> **교훈 — 지운 것의 재료는 남겨 둔다.** 캐러셀은 걷었지만 그 때 만든 webp 와
> 커밋에 남은 글이 덱을 짓는 밑감이 됐다.

## 14. PBL 이 **파트 04 로 독립했다**

아침에 세운 PBL 상자가 저녁에는 **한 파트**가 됐다. 사용자가
「이 부분을 파트 04 로 해줘. 제목은 PBL 이야」라 했다.

### 파트가 일곱에서 여덟로

```
전                          후
01 국내 사례                01 국내 사례
02 해외 사례                02 해외 사례
03 직접 만들어 보기·공모전   03 직접 만들어 보기 · 공모전
04 책                       04 PBL — 문제에서 출발한다   ← 신설
05 이론 슬라이드             05 책
06 연구                     06 이론 슬라이드
07 국내 자료실               07 연구
                            08 국내 자료실
```

파트 03 에서 **원형 맵 · 여덟 장 만화 · PBL · 아홉 곳 카드 · URL 정리**를 떼어 냈다.
공모전 카드는 03 에 남는다 — 앞은 **낼 자리**, 뒤는 **그 아이디어가 무엇이 되었는지**다.

> **교훈 — 번호를 밀면 본문이 거짓말을 한다.**
> 헤딩 넷만 고치면 끝이 아니었다. 본문에서 파트를 가리키던 곳이 **일곱**이었다 —
> 로드맵 두 칸 · 제주 논문 · 척도개발 안내 둘 · 구철모 각주 · CSS 주석.
> `파트 0N` 을 전부 뽑아 하나씩 대조하고서야 끝났다.

### 파트 알약 여덟

강의실 바 아래 빈 자리에 **01~08 알약**을 두고 각 파트 머리글에 `id="part0N"` 을 달았다.
페이지가 길어 위에서 바로 뛴다. `:target { scroll-margin-top: 78px }` 으로 뛰어간 제목이 헤더에 가리지 않는다.

### 상자를 세 번 벗겼다

같은 요청이 하루에 세 번 왔다 — **척도개발** · **PBL** · 그리고 다시 **PBL 접기**.

| 무엇 | 어떻게 |
|---|---|
| 척도개발 | 상자를 버리고 파트 05 와 같은 꼴(머리글 + 한 줄 + 덱)로 |
| PBL | `case-box.pbl` 에 `plain` 을 더해 테두리 · 바탕만 0 으로 |
| PBL 접기 | 넷을 접었다가 **같은 날 도로 풀었다** — 상자를 벗겨 길이가 줄자 접을 이유가 없어졌다 |

> **교훈 — 클래스를 떼지 말고 `plain` 을 더한다.**
> `cb-title` · `cb-lead` 의 서식이 `.case-box` 에 묶여 있어, 클래스를 떼면
> 제목과 머리글 모양이 함께 사라진다. 겉모습만 끄는 변형자를 더하는 편이 안전하다.

## 15. **내가 지운 CSS 가 두 번 다른 곳을 망가뜨렸다** (같은 뿌리의 사고 → 16 · 17절)

오늘 가장 부끄러운 대목이다. 죽은 CSS 를 정규식으로 걷다가 **바로 뒤에 붙어 있던 살아 있는 블록까지** 삼켰다.

```python
re.search(r'/\* 척도개발 상자 —.*?
    \}
(?=    /\* 노란 알약)', ...)
#           ↑ 지울 블록              ↑ 여기까지 — 사이에 있던 것도 함께 사라진다
```

`.*?` 가 **두 표지 사이의 모든 것**을 먹었고, 그 사이에는 방금 만든 **덱 CSS** 와 **공모 카드 목록 CSS** 가 있었다.

### 증상이 셋으로 나타났다

| 보인 것 | 잃은 규칙 |
|---|---|
| 「1 현장자료**문헌 · 사례…**」 붙음 | `display: grid` |
| 숫자가 **두 번** | `list-style: none` (`<ol>` 기본 번호가 드러남) |
| 세로 **ㅣ 바** | `border-left: 0` (`learn.css` 의 `.reslist li` 좌측 선이 살아남) |

사용자는 **「내 눈에는 변화가 없어」**라 했다. 표 수정까지 함께 날아갔으니 맞는 말이었다.

> **교훈 — 정규식으로 CSS 블록을 지울 때는 `.*?` 로 두 표지를 잇지 않는다.**
> 지울 블록의 **시작과 끝을 스스로 닫는 패턴**으로 잡거나, 줄 단위로 세어서 지운다.
> 그리고 **지운 뒤에는 남아 있어야 할 선택자를 하나 골라 grep 으로 확인**한다.

두 번째 사고는 첫 번째를 고치는 커밋에서 또 났다 — 같은 정규식이 `ax-kw` 를 물고 갔다.
**한 번 당한 패턴을 그대로 다시 쓴 것**이 문제였다.

## 16. 척도개발 덱을 **다섯 번 손봤다**

세우고 나서가 진짜였다. 순서 · 합침 · 밀도 · 색 · 정렬을 차례로 고쳤다.

### 순서 — 표를 맨 앞으로, 그림을 그다음으로

```
처음                     최종
01 이것만은              01 요인 패턴      ← 07 에서 올라옴
…                       02 장면으로       ← 09 에서 올라옴
07 요인 패턴             03 이것만은 · 복습 목표
…                       04 만드는 법  05 요인 용어
09 장면으로              06 산업 비교  07 공통과 차이  08 읽는 흐름
                        09 기억할 3문장  10 셀프체크 · 출처
```

**표로 보고 → 그림으로 익히는** 순서가 됐다. 다섯 산업에 든 요인을 ● 로 한눈에 보는 표가
맨 앞이고, 그 요인 여덟이 실제 장면에서 어떻게 나타나는지가 바로 뒤다.

### 합침 — 열한 장에서 열 장으로

「이것만은 기억하자」와 「복습 목표와 핵심 문장」이 **같은 말을 두 장에 나눠** 하고 있었다.
한 장으로 묶으면서 **내용은 하나도 버리지 않았다** — 겹치던 것은 02 의 요약 한 줄뿐이고,
그 내용은 03 의 ① ② ③ 에 그대로 있다.

### 밀도 — 세 줄을 한 줄로

| 어디 | 전 | 후 |
|---|---|---|
| 요인 용어 여덟 | 한글 / 영어 / 설명 **세 줄** | **「한글 (영어) 설명」 한 줄** |
| 기억할 3문장 | 번호와 글이 **칸으로 갈림** | **붙여서 한 줄**, 왼쪽 정렬 |
| 산업 비교표 | 열 너비 11 · 13 · 30 · 28 · 18% | **다섯 열 20% 씩 균등** |

### 색 — 네 덩어리를 층마다 갈랐다

「공통과 차이」 네 줄이 전부 같은 베이지였다. 층마다 색을 주니
**어디까지가 공통이고 어디부터 갈리는지가 색으로** 읽힌다.

```
ALL 5              초록   편의성 + 스마트인프라
여행 · 외식 · 컨벤션  파랑   기술통합성 + 정보성 + 신뢰성
숙박 · 항공          갈색   개인화 + 상호작용성
항공만              빨강   보안성
```

이 페이지가 이미 쓰는 색들이라 새로 만들지 않았다.

### 그 사이 사고 하나 — **남의 덱 점을 덮어썼다**

순서를 바꾸며 점 이름표를 고치는데 `.deck-dots` 를 **문서 처음부터 찾았다.**
그 바람에 **파트 06 이론 슬라이드 덱(5장)에 척도개발 점 열하나**가 들어갔다.

> **교훈 — 오늘 세 번째로 같은 종류의 실수다.**
> 정규식 CSS 삭제 · `ax-kw` · 덱 점 — 전부 **범위를 좁히지 않고 문서 전체에서 찾은** 탓이다.
> 부품이 둘 이상인 페이지에서는 **먼저 그 부품의 구간을 잡고 그 안에서만** 찾아야 한다.
> 고친 뒤에는 **덱마다 슬라이드 수와 점 수가 같은지** 세어 확인했다(5·5 / 10·10).

## 17. **접기 하나가 파트 셋을 삼키고 있었다**

사용자가 세 번 말했다 — **「이거 파란 박스에서 빼라고 했는데 수행했어?」**
세 번째에야 제대로 들여다봤고, 내가 만든 사고였다.

### 무슨 일이었나

안동 실습 접기를 단계 2 안으로 옮길 때(`6689ad2`) **닫는 태그 다섯을 원래 자리에 두고 왔다.**

```
옮긴 것   <details> … </details>   ← 안쪽 지오코딩 접기의 </details> 까지만
남긴 것   </li></ol></li></ul></details>   ← 원래 자리(파트 04)에 그대로
```

그 바람에 바깥 접기가 **단계 3 · 파트 02 · 파트 03 을 통째로 품었다.**
접기 하나가 **372줄**을 삼키고 있었다.

### 검사로는 안 잡혔다

| 검사 | 결과 |
|---|---|
| 태그 균형(`unclosed`) | **0 — 정상** |
| 파서 오류 | **없음** |

**구조가 깨진 것이 아니라 「어디서 닫히느냐」가 틀렸기 때문이다.**
여는 태그와 닫는 태그 수는 내내 맞았다.

> **교훈 — 블록을 옮길 때는 「첫 번째 닫는 태그」를 끝으로 삼지 않는다.**
> 안에 같은 이름의 태그가 중첩돼 있으면(`<details>` 안의 `<details>`)
> 첫 번째 `</details>` 는 안쪽 것이다. **깊이를 세어서** 짝을 찾아야 한다.
> 그리고 **태그 균형 검사는 이 종류의 사고를 못 잡는다** — 옮긴 뒤
> 「그 블록이 몇 줄을 품고 있는지」를 세어 보는 검사가 따로 필요하다.

### 같은 날 세 번 — 범위를 안 좁힌 탓

15 · 16 · 17절이 전부 같은 뿌리다.

```
15절  정규식 CSS 삭제   → 두 표지 사이의 살아 있는 블록까지 삼킴
16절  .deck-dots 검색   → 남의 덱 점을 덮어씀
17절  첫 </details>     → 블록의 끝을 잘못 잡음
```

셋 다 **「찾는 범위를 좁히지 않은 것」**이다. 오늘 배운 가장 비싼 교훈이다.
